# commit 스킬 — 저장소 규칙 기반 원자적 커밋

이 스킬은 **격리된 fork 컨텍스트**에서 실행된다 — 호출한 대화의 맥락을 볼 수 없다. 따라서 **워킹트리 상태(`git status`/`git diff`)와 인자로 받은 의도**만으로 판단한다. 인자에 커밋 의도·분할 계획이 담겨 온다.

## 절대 규칙 (위반 금지)

1. **AI 귀속 금지** (`includeCoAuthoredBy = false`): `Co-Authored-By: Claude`, "Generated with Claude Code" 같은 AI 표시를 커밋 메시지 본문·푸터에 **절대** 넣지 않는다. 완전 익명.
2. **`git add .` / `git add -A` 금지**: 파일 경로를 명시해 스테이징하고 `git diff --cached`로 범위를 검증한다.
3. **범위 외 변경은 커밋하지 않는다**: 인자로 받은 의도에 없는 변경(디버깅 흔적·의도 외 asset·ProjectSettings 등)이 워킹트리에 있으면 **커밋을 멈추고 사용자에게 보고**한다 — 절대 함께 끌어오지 않는다.
4. **이력 재작성 금지**: 이미 생성된 커밋을 사용자 별도 요청 없이 amend·rebase·squash 하지 않는다.

## 실행 절차

### Step 1 — 병행 커밋·현재 상태 파악
```bash
git log -1 --stat | cat   # 사용자 병행 커밋 감지 — 이미 커밋된 파일 재커밋 방지
git status --short          # 워킹트리 전체
```
- `git log -1`에 인자가 가리키는 파일이 **이미 커밋돼 있으면** 재커밋 시도 금지 — 중복·빈 커밋 위험. 사용자에게 "이미 커밋됨"을 보고하고 종료.

### Step 2 — 논리적 그룹 결정
- 인자의 분할 계획을 1차 기준으로 삼는다. **파일 수가 아니라 논리적·원자적 작업 단위**로 그룹핑.
  - 하나의 기능·수정·마이그레이션을 완성하는 파일은 같은 커밋. 관련 없는 변경은 분리.
  - **Unity 에셋과 대응 `.meta`는 같은 커밋** (생성·수정·삭제·이름 변경 모두). 신규 `.cs`의 `.meta` 짝이 워킹트리에 있는지 `git status`로 확인 — 짝이 없으면(사용자가 아직 Unity를 안 연 상태) 사용자에게 알리고 `.meta` 없이 커밋할지 확인.
  - 생성 코드와 그 생성 설정·원본 스키마는 같은 커밋. 서드파티 패키지 동일 버전 파일은 하나의 패키지 단위.
- 각 커밋은 가능하면 독립적으로 cherry-pick·revert·bisect 가능하고 컴파일 가능한 상태여야 한다. 분리하면 컴파일이 깨지는 상호 의존 변경은 한 커밋으로 묶는다.
- **인자가 모호하거나 워킹트리에 인자로 설명되지 않은 변경이 있으면** — 임의 판단하지 말고 사용자에게 확인 요청 후 종료(절대 규칙 3).

### Step 3 — 그룹별 스테이징·검증
```bash
git add <명시 경로 1> <명시 경로 2> ...   # 절대 git add . 금지
git diff --cached --stat                   # 스테이징 범위가 의도와 정확히 일치하는지 검증
```
- 스테이징 결과가 그 그룹 의도와 다르면 `git restore --staged`로 되돌리고 재구성.

### Step 4 — 커밋 (Conventional Commits 한글 적용)
- 메시지는 **반드시 한글**로 작성한다. Conventional Commits 구조를 이 저장소 이력에 맞게 옮긴 형식:
  ```
  <유형>(<범위>): <제목> — <세부·근거> (<카드 N>)

  <본문 — "왜"를 설명, 한 줄 72자 내외>

  <푸터 — 이슈·카드 참조>
  ```
  범위(scope)·세부·카드 번호·본문·푸터는 모두 선택 — 헤더 한 줄로 충분한 커밋이 대부분이다.
- **유형은 아래 표의 한글 유형만 사용** (Conventional Commits 대응):

  | 유형 | 대응 | 용도 |
  |------|------|------|
  | `기능` | feat | 새 기능·시스템 추가 |
  | `수정` | fix | 버그·회귀 수정 |
  | `리팩토링` | refactor | 동작 불변 구조 변경 |
  | `성능` | perf | 성능 개선 |
  | `테스트` | test | 테스트 추가·수정 |
  | `문서` | docs | 문서만 변경 |
  | `정리` | chore | 빌드·도구·의존성·잔재 제거 |
  | `데이터` `메타` `설정` `아키텍처` `회고` `패키지` `도구` | (저장소 고유) | 위 7종에 안 맞는 이 저장소 고유 단위 |

  (`코드` 는 과거 이력 유형 — 신규 커밋은 `기능`/`수정`/`리팩토링` 으로 세분한다)
- **제목은 선언형 현재 서술**("~한다" 또는 명사구) — 영어 명령형("Fix", "Add")의 한글 대응. 과거형("~했다"/"~했음") 금지, 마침표 없음, 50자 내외.
  - 예: `기능(연출): 족보 완성 플로팅 텍스트를 해금한다 (카드 30)`
  - 예: `테스트: 선수전 NUnit 23케이스 — terminal 6종 전수·총 칩 보존`
- **본문은 "무엇"이 아니라 "왜"** — 무엇이 바뀌었는지는 diff가 이미 말한다. 설계 근거·트레이드오프·거부한 대안을 빈 줄 뒤 bullet로. 자명한 변경이면 본문 생략.
- 푸터에는 이슈·카드·관련 커밋 참조만 넣는다. **AI 귀속 표시 절대 금지**(절대 규칙 1) — `Co-Authored-By` trailer는 어떤 이름으로도 추가하지 않는다.
- 그룹이 여러 개면 Step 3~4를 그룹마다 반복.

### Step 5 — 최종 보고
```bash
git status --short          # 워킹트리 clean 확인
git log --oneline -N | cat  # 생성한 커밋 확인 (N = 이번 커밋 수)
```
- 보고: 생성한 커밋 해시·메시지 목록, 워킹트리 clean 여부, 범위 외 변경 발견 시 별도 강조.

## 자가 검증 체크리스트 (커밋 직전)
- [ ] `git add .`/`-A`를 쓰지 않았는가
- [ ] `git diff --cached`로 각 커밋 범위를 검증했는가
- [ ] 신규 `.cs`의 `.meta` 짝을 확인했는가 (Unity 에셋 커밋 시)
- [ ] 인자로 설명되지 않은 범위 외 변경을 함께 커밋하지 않았는가
- [ ] 유형이 대응 표의 한글 유형이고 제목이 선언형 현재 서술인가
- [ ] 본문이 있는 커밋이라면 "무엇"이 아니라 "왜"를 설명하는가
- [ ] 커밋 메시지에 AI 귀속 표시가 전혀 없는가
- [ ] 이미 커밋된 파일을 재커밋 시도하지 않았는가
