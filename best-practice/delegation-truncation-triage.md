# 에이전트 절단 트리아지 — 3상태 분류와 재위임 처방

서브에이전트가 `maxTurns` 한계로 절단됐을 때 **절단 시점의 상태는 셋으로 갈린다**. 상태를 구분하지 않고 재위임하면 상태별로 서로 다른 사고가 발생한다. Double Down Slice A 카드 27~28(2026-07-28) 한 세션에서 절단 6회를 실측하며 도출.

## 1. 3상태 분류

| 상태 | 절단 시점 | 산출물 | 상태 무시 재위임의 결과 |
|------|----------|--------|------------------------|
| **ⓐ 검증 절단** | 편집 **완료 후** 검증·보고 단계 | 편집 100% 반영 | **중복 편집** — 같은 수정이 두 번 적용되거나 직전 결과가 되돌려짐 |
| **ⓑ 탐색 소진** | 탐색만 하다 예산 소진 | **편집 0건** | 재위임은 필요하지만, 같은 프롬프트면 **같은 지점에서 또 절단** |
| **ⓒ 절반 절단** | 항목 일부만 완료 | 부분 반영 | **완료분 되돌림 + 미착수분 누락** (가장 비싼 오판) |

실측 6회의 분포:

- ⓐ — 카드 27 Part B(Jarvis), 카드 27.5(Ava): 편집은 끝나고 검증 쿼리 중 절단
- ⓑ — 카드 27 Part C(신규 Jarvis 인스턴스, 36 tool use 전량 재탐색), 카드 28 첫 시도(Ava, 40 tool use 전량 탐색)
- ⓒ — 테스트 작성(Sonny): `BoardModelTests` 완료 / `StepPlayerTests` 미착수

## 2. 판별 3종 (재위임 **전** 의무)

1. **`git status --short`** — 수정·신규 파일 목록. 비어 있으면 ⓑ 확정.
2. **산출물 mtime 대조** — `ls -la <대상 디렉터리>`로 위임 시작 시각 이후 변경 여부 확인. `git status`가 비어도 gitignore 대상·scratchpad 산출물이 있을 수 있다.
3. **처방 grep** — 위임 프롬프트가 요구한 **심볼·시그니처·케이스명이 실제로 들어갔는지** 개별 확인. **ⓐ와 ⓒ를 가르는 유일한 수단** — 파일이 수정됐다는 사실은 "요구 항목이 전부 들어갔다"를 뜻하지 않는다.

판별 결과 매핑:

| `git status` | 처방 grep | 판정 |
|---|---|---|
| 변경 0건 | — | ⓑ |
| 변경 있음 | 요구 항목 전부 확인 | ⓐ |
| 변경 있음 | 일부만 확인 | ⓒ |

**보조 신호(판별 3종을 대체하지 않음)**: 절단 보고가 "확인합니다 / 검토합니다" 같은 탐색 문장으로 끝나면 **편집은 이미 끝났을 가능성 80%+**(ⓐ). 다파일 작업에서 절단 시점의 대다수는 편집 **후** 검증 쿼리 단계다.

## 3. 상태별 처방

**ⓐ 검증 절단** — 재수정 금지.

- `git diff --stat`으로 실제 수정 상태를 먼저 확인하고, 이미 반영돼 있으면 **같은 내용을 다시 위임하지 않는다**
- 남은 일은 검증뿐이므로 **read-only 검증자를 별도 인스턴스**로 호출 ([evaluation.md](../.claude/rules/evaluation.md) 작성자/검증자 분리)

**ⓑ 탐색 소진** — 재위임하되 **프롬프트를 재설계**(§4). 같은 프롬프트 재전송은 같은 결과를 반복한다.

**ⓒ 절반 절단** — 범위를 잘라서 재위임.

- 프롬프트에 **완료분을 명시**: "`BoardModelTests`는 완료됐다. 열지도 수정하지도 마라"
- **미착수분만 작업 범위**로 지정 ([unity-delegation.md](../.claude/rules/unity-delegation.md) 범위 보존 의무)

## 4. 예방 — 탐색 소진(ⓑ)의 원인은 코디네이터 프롬프트

ⓑ는 에이전트 능력 문제가 아니라 **프롬프트 과적재로 turn 예산을 탐색에 태운 결과**다. 정보를 많이 준 것이 원인이었다.

**실측**: 카드 28 첫 위임에 ① 확정된 구조 설명 ② 렌더링 계획서 ③ 데이터 원천 5종 ④ "먼저 확인하라" 지시를 한 프롬프트에 담았더니, Ava가 **40 tool use를 전부 확인·탐색에 소모하고 편집 0건**으로 절단. "먼저 확인하라"는 지시가 참조 5종을 전수 열람하게 만들었다.

**처방 4가지**:

- **Part 분할** — 파일 5개 이상 수정 예상 시 Part A/B로 나눠 각 15 turn 이내로 설계
- **탐색 상한 명시** — "편집만 하고 검증·분석은 생략", "이미 제공한 정보로 충분하니 **재탐색 금지**", "보고는 3줄 이내"
- **한 메시지에 A+B 동시 지시 금지** — "감사(read-only) + 구현(edit)"을 한 에이전트에 함께 시키면 감사가 예산을 먹고 구현이 절단된다. 분리 호출.
- **보고 포맷 사전 고정** — 섹션 수·줄 수 상한을 미리 지정해 보고 단계의 turn 소모를 억제

### 4-1. 좌표 제공 원칙 — 결정과 좌표는 별개 비용이다

위 처방은 "필요한 결론만 인용하라"까지만 말하고 **무엇이 '결론'인지**를 정의하지 않았다. 그 공백에서 같은 절단이 반복된다 — Double Down 턴 엔진 재구성(2026-08-29) 한 세션 **5회 재발**.

프롬프트가 주는 것은 두 종류이고 **서로를 대체하지 못한다**.

| | 주는 것 | 없으면 |
|---|---|---|
| **결정** | 무엇을 할지 확정 — 설계, 선택된 옵션, 합격 기준 | 에이전트가 설계를 재발명하거나 되묻는다 |
| **좌표** | 그것이 어디 있는지 — 파일:줄, 심볼, 현재 코드 형태 | 에이전트가 **찾는 데 예산을 태운다** |

결정만 완벽하게 적힌 짧은 프롬프트가 예산을 다 태울 수 있는 이유가 이것이다. 짧다는 것은 과적재의 반대일 뿐 **좌표가 있다는 뜻이 아니다**.

**통한 지시 / 실패한 지시** (같은 세션 실측):

| 통한 지시 — 좌표 | 실패한 지시 — 읽기 요구 |
|---|---|
| `Foo.cs:120-138` 처럼 파일:줄번호 | "선례를 먼저 읽어라" |
| `new X(` grep 결과를 **표로 붙임**(생산 지점 전수) | "X 를 grep 해 같은 계급으로 맞춰라" |
| 함수 시그니처 전문 인용 | "기존 파일의 픽스처 방식을 미러링하라" |
| 기존 코드 블록 통째 인용 | "관련 테스트를 참고해서" |

오른쪽은 전부 **읽기를 요구하는 지시**다. 읽을 대상이 하나뿐이어도 에이전트는 그 하나를 찾기 위해 주변을 연다.

**판정 규칙**: 보내기 전에 프롬프트의 동사를 훑는다. **"읽어라 / 찾아라 / 맞춰라 / 미러링하라 / 참고하라"가 있으면 좌표 누락 신호** — 그 자리에 grep 결과나 인용을 대신 넣는다.

**비용 계산**: 코디네이터가 grep 6번 하는 비용 < 에이전트가 30번 하는 비용. 코디네이터의 grep 은 결과를 재사용할 수 있고(같은 표를 여러 위임에 붙임), 에이전트의 탐색은 인스턴스가 끝나면 버려진다.

**참조 문서 링크는 좌표가 아니다**: 링크는 "여기 어딘가에 있다"이므로 읽기 요구와 같다. 필요한 결론을 인용하고, 링크는 "판단이 막힐 때만 열어라"로 조건부 제공한다.

## 5. 재개(SendMessage)로 ⓑ를 구조적으로 줄이기

직전 카드 산출물을 소비·확장하는 작업을 신규 인스턴스로 띄우면 **재탐색이 절단 임계를 먼저 소진**한다(카드 27 Part C 실측: 36 tool use 재탐색, 편집 0건). 판단 기준·운영 규칙: [sequential-delegation-context-reuse.md](sequential-delegation-context-reuse.md)

## 6. 자기 참조 심볼 — 절단돼도 컴파일되게 쓰는 순서

절단이 남기는 것이 "미완성 산출물"이 아니라 **컴파일 불가 어셈블리**인 경우가 있다. 케이스 본문은 들어갔는데 그 안에서 부르는 **헬퍼·상수가 아직 정의되지 않은** 채 예산이 끊긴 것이다. 이때 손실은 산출물 범위를 넘는다 — 같은 어셈블리의 기존 테스트 전량이 함께 못 돈다.

Double Down 획득패 4분류(2026-08-04) 한 세션 3회:

| 회차 | 미정의로 남은 심볼 |
|---|---|
| 1 | `PumpForSeconds` |
| 2~3 | `SsangpiDefinitionIds` · `TallySampleSeeds` · `FourKinds` · `PiSample` · `AssertTallyMirrorsCaptured` |

**기존 룰이 못 잡는 이유**: [evaluation.md](../.claude/rules/evaluation.md) 의 "참조 실재를 grep 으로 확인"은 **남의 심볼**을 전제한다. 이건 작성자가 **나중에 자기가 정의할 예정**이던 심볼이라, 작성 시점에 grep 하면 없는 것이 정상이다 — 규칙이 발화하지 않는다. 절단을 겪고 나서야 미정의로 확정된다.

**처방 — 작성 순서 역전**: 헬퍼·상수·픽스처를 **먼저 정의하고 사용부를 나중에** 쓴다. 어느 지점에서 끊겨도 그때까지의 산출물이 컴파일된다(정의만 있고 쓰는 데가 없는 것은 컴파일 통과). 반대 순서는 끊긴 지점이 어디든 컴파일 실패다. 산출물의 완성도는 예산에 비례하지만 **컴파일 가능성은 순서에만 달려 있다**.

**위임 프롬프트 한 줄**:

> 헬퍼·상수·픽스처를 **먼저 정의**하고 그것을 쓰는 케이스를 나중에 작성하라. 예산이 끊겨도 그 시점의 파일이 컴파일되어야 한다.

**수령 게이트**: 기존과 동일 — 컴파일·실행 통과 전까지 "작성 완료"가 아니라 **"컴파일 미검증"**([evaluation.md](../.claude/rules/evaluation.md)). §2 처방 grep 은 요구 항목의 유무만 보므로 미정의 심볼을 걸러내지 못한다.
