# 부산물 잔재의 거짓 신호 — 게이트 판정자 검증

판정자를 게이트에 넣기 전에 **그것이 거짓말하는 조건을 함께 확인**해야 한다. 특히 **부산물(락 파일·PID 파일·마커 파일·`.tmp`)은 생산자가 비정상 종료하면 지워지지 않는다** — 잔재가 기본값이다. 부산물의 존재는 "생산자가 살아 있다"의 증거가 아니라 "언젠가 생산자가 있었다"의 증거일 뿐이다.

## 1. 룰

- **부산물을 상태 판정자로 쓰지 않는다.** 판정하려는 것이 "지금 실행 중인가"라면 판정자는 **프로세스 존재** 같은 직접 관측이어야 한다
- 부산물을 쓸 수밖에 없으면 **잔재 판별을 함께 붙인다** — 기록된 PID 의 생존 확인, mtime 임계, 또는 직접 관측과의 AND 결합
- **게이트는 도입한 실행에서 한 번은 반증을 시도한다.** 도입 직후 "정상 상태에서도 게이트가 걸리는지" 1회 확인하지 않으면 거짓 양성이 다음 실행까지 그대로 간다

## 2. 실측 — UnityLockfile 거짓 양성

Unity 배치 테스트가 exit 1 로 실패했다. `Temp/UnityLockfile` 존재를 보고 "에디터가 프로젝트를 점유 중"으로 판정해 게이트로 넣었고, **바로 다음 실행에서 거짓 양성**이 났다.

실제 인과는 반대였다.

```
컴파일 에러 → 배치 프로세스 비정상 종료 → 락 파일 미삭제 → 잔재
                                              ↓
                        게이트: "에디터 점유 중" (거짓)  ← 원인과 결과를 뒤집어 읽음
```

- 락 파일은 **실패의 결과**인데 게이트는 그것을 **실패의 원인**으로 읽었다
- 참 판정자는 `Unity.exe` **프로세스 존재**. 락 파일은 프로세스가 남긴 흔적일 뿐
- 게이트가 한 번 서면 이후 모든 실행이 같은 거짓 판정을 받아 **진짜 원인(컴파일 에러) 조사가 시작조차 안 된다** — 거짓 양성 게이트의 비용은 1회 오판이 아니라 조사 경로의 봉쇄다

## 3. Unity 배치 모드 exit 1 판별표

부수 관찰: Unity 배치 실행은 **프로젝트 점유와 컴파일 에러가 똑같이 exit 1** 이다. 종료 코드만으로는 구분 불가 — 아래 조합으로 판별한다.

| 컴파일 에러 grep | 결과 XML | 판정 | 다음 행동 |
|---|---|---|---|
| 0건 | 0건 | **프로젝트 점유** (또는 기동 실패) | `Unity.exe` 프로세스 확인 후 에디터 종료 |
| 있음 | 0건 | **컴파일 실패** | 로그의 첫 에러부터 수정 — 테스트는 시작도 안 했다 |
| 0건 | 있음 | **테스트 실패** | 정상 실패. XML 의 실패 케이스 분석 |
| 있음 | 있음 | 부분 컴파일 + 실행 | 에러 먼저 해소 후 재실행 (결과 신뢰 불가) |

**핵심**: "결과물이 아예 없다"와 "결과물이 실패를 담고 있다"는 전혀 다른 실패다. 결과 XML 의 **생성 여부** 를 exit 코드보다 먼저 본다.

## 4. 게이트 도입 체크리스트

새 판정자를 자동 게이트·훅·스크립트에 넣기 전에:

- [ ] 이 신호는 **무엇의 부산물**인가? (직접 관측인가, 흔적인가)
- [ ] 생산자가 **비정상 종료하면 남는가**? 남는다면 잔재 판별을 붙였는가
- [ ] **직접 관측 대체재**가 있는가? (프로세스 목록, 포트 점유, API 응답)
- [ ] 게이트가 걸렸을 때의 메시지가 **원인이 아니라 관측 사실**을 말하는가? ("점유 중" 대신 "락 파일 존재 + 프로세스 없음 = 잔재 의심")
- [ ] 도입 직후 **정상 상태에서 1회 반증** 했는가
