# 테스트 목적 전환 — 전제가 소멸한 테스트를 불변식 계약으로 되살리기

재설계로 테스트의 **전제가 사라졌을 때** 선택지는 보통 둘로 좁혀진다: 삭제하거나, 새 숫자를 다시 박아 넣거나. 셋째 선택지가 **목적 전환** — 같은 테스트를 **구현 서술에서 불변식 검증으로 다시 겨냥**하면 값이 바뀌어도 살아남는다. Double Down Slice A 보드 레이아웃 재설계(2026-07-28)에서 실측.

## 실측 사례

보드 레이아웃을 ScriptableObject + 화면 공간 예산 방식으로 재설계하면서 `*_MatchesLegacyPosition`(옛 하드코딩 좌표와의 동치 검증)의 전제가 소멸.

| 선택지 | 결과 |
|--------|------|
| 삭제 | 해당 영역의 회귀 감지가 통째로 사라짐 |
| 새 좌표 재하드코딩 | 다음 레이아웃 조정 때 또 깨짐 — 테스트가 구현의 그림자를 계속 따라다님 |
| **목적 전환** ✓ | "무슨 조합이든 밴드를 넘지 않는다" **공간 예산 봉쇄 계약**으로 재겨냥 |

전환 후 테스트는 좌표 값이 바뀌어도 통과하고, **정말 위험한 회귀(카드 수·폭이 늘어 밴드를 넘는 경우)만** 잡는다.

## 구현 서술형 vs 불변식형 판정

| 축 | 구현 서술형 (취약) | 불변식형 (내구성) |
|----|------------------|------------------|
| 단언 대상 | 특정 좌표·개수·문자열 리터럴 | 범위·순서·관계·보존량 |
| 이름 | `*_MatchesLegacyPosition`, `*_Returns_42` | `*_StaysWithinBudget`, `*_PreservesOrder` |
| 재설계 시 | 값이 바뀌면 즉시 실패 (거짓 경보) | 계약을 깨야만 실패 (진짜 경보) |
| 실패가 알려주는 것 | "값이 달라졌다" | **"약속이 깨졌다"** |

**핵심 질문**: 이 테스트가 실패했을 때 **"구현이 바뀌었네"** 라고 반응하게 되면 구현 서술형이다. **"이건 고쳐야 하는데"** 라고 반응하면 불변식형이다.

## 전환 절차 3단계

1. **원래 지키려던 것을 언어로 복원** — "옛 좌표와 같아야 한다"가 아니라 그 좌표가 **왜** 그 값이었는지. 실측에서는 "카드가 화면 밴드를 벗어나지 않는다"였다.
2. **그 목적을 값 독립 술어로 재작성** — 리터럴 비교를 범위·관계 단언으로 교체. 필요하면 입력을 **조합 전수/경계값**으로 넓혀 계약의 강도를 올린다.
3. **이름을 목적에 맞게 개명** — 이름이 구현을 서술하면 다음 사람이 다시 구현 서술형으로 되돌린다. 개명은 선택이 아니라 전환의 마무리.

## 언제 삭제가 옳은가

목적 전환이 항상 답은 아니다. 다음이면 삭제한다:

- 복원한 "원래 목적"이 **이미 다른 테스트가 커버** — 중복 계약은 유지 비용만 남는다
- 복원해 보니 목적이 **마이그레이션 한정**(옛 구현과의 일시적 동치 보장) — 마이그레이션 종료와 함께 수명이 끝난 테스트
- 값 독립 술어로 바꾸면 **아무것도 단언하지 않게 되는** 경우 — 통과가 보장된 테스트는 위양성 안전망일 뿐
