## § 1. Phase 정의 SSOT 우선 룰

명세 문서가 **두 가지 차원의 SSOT**를 동시에 보유할 때 우선순위 규칙.

### 1-1. 두 차원의 정의

| 차원 | 의미 | 예시 |
|------|------|------|
| **What 차원** (인벤토리 SSOT) | 최종 형태에 어떤 위젯/모듈/기능이 결국 존재하는가 | `/dashboard` 위젯 인벤토리, 최종 컴포넌트 트리, API 엔드포인트 목록 |
| **When·How 차원** (Phase 정의 SSOT) | 어느 단계에 / 어느 데이터 소스로 / 어느 의존성 제약 하에 | "Phase 1은 1개 페이지에 집중, Phase 0 자산 재사용만, 데이터 yfinance only, KIS는 후속 단계" |

**둘 다 SSOT인데, Phase 분해 작업의 결정 기준은 항상 When·How 차원이 우선**:
- What 차원은 "어디로 가는가" — 분해 결정에 직접 사용 금지
- When·How 차원은 "지금 무엇을 하는가" — 분해 결정의 직접 입력

### 1-2. 분해 작업 시작 전 의무 절차

1. **Phase 정의 인용**: 대상 Phase의 범위 정의(데이터 소스 / 페이지 범위 / 의존성 제약 / 명시적 후속 이관 항목)를 **그대로 인용해서 작업 컨텍스트 상단에 박제**
2. **데이터 소스 제약 명시**: "이 Phase에서 사용 가능한 데이터 소스는 [X]. [Y]는 후속 단계 의존"
3. **인벤토리 매핑은 그 다음**: 인벤토리에서 자산을 가져올 때 매 항목에 대해 "Phase 정의 제약 위반 없는가" 점검
4. **위반 시 자동 거부**: 인벤토리에는 있어도 Phase 제약 위반이면 자산화 거부 + § 2 룰로 처리

### 1-3. 합리화 자동 차단 신호

다음 표현이 머릿속/문서에 등장하면 **Phase 정의 SSOT 위반 신호**로 판정 → 즉시 차단:

- "10개로 떨어지면 깔끔" / "N개 맞추면 보기 좋음" → 인벤토리 매수 미학이 Phase 제약을 덮는 합리화
- "미리 박으면 후속 Phase가 가벼움" → Phase 분리 자체의 부정. 분리 이유가 있는데 우회
- "[필요 데이터 소스] 없이 어떻게든" → Phase 제약 위반의 직접 표명
- "[자산 X]는 시각만 placeholder로" → 자산화는 인터페이스/계약을 박는 행위. placeholder도 자산
- "어차피 후속에서 손볼 거" → 후속 Phase 작업을 현재 Phase에 미리 끌어옴

위 표현 시도 시 헌법 §0-1 Step 2 (합리화 회피) 적용 → 즉시 차단, Phase 정의 재인용 후 재분해.

### 1-4. 인시던트 증거

**Endurance Phase 1 분해 1차안 (2026-05)**:
- `reports/tl-dr-hashed-unicorn.md` Line 17-19 (`/dashboard` 위젯 인벤토리) 만 보고 LPPL / IRF / 외국인기관 수급을 Phase 1 자산으로 분해
- 같은 문서 Line 103-106의 Phase 1 범위 정의("1개 페이지 집중 / Phase 0 자산 재사용만 / 데이터 yfinance only / KIS는 후속 단계")를 무시
- 합리화 4종 동시 시도 (위 § 1-3의 4개 신호 모두 발현)
- 사만다 시니어 검토에서 자동 차단됨 → 본 룰 박제 트리거

## § 2. YAGNI Asset Rejection — 3-way 분기 의무

Phase 분해 중 발견한 "좋아 보이는 아이디어"의 처리 경로. **거부 결정도 명시 박제 의무** — 거부 사유 없이 누락되면 다음 Phase에서 같은 후보 재등장 (회귀).

### 2-1. 3-way 분기

분해 중 등장한 아이디어는 정확히 다음 셋 중 하나로 처리:

| 경로 | 처리 방식 | 박제 위치 |
|------|----------|-----------|
| **① 자산화** | 현재 Phase 범위 내 자산으로 채택 | Phase 자산 목록 |
| **② 후속 Phase 이관** | 명시적 후속 단계로 이관 | 명세 README의 "Phase N 이관 항목" 섹션 |
| **③ 자산 외 박제** | 자산화 거부 + 거부 사유 + 대체 처리 경로 명시 | `best-practice/*` 또는 헌법 보강 등 자산 외 산출물 |

**셋 중 하나로 명시 처리 안 된 채 누락되면 회귀 가능**. "그냥 안 함"은 허용되지 않음.

### 2-2. 거부 결정의 박제 표준

경로 ③ (자산 외 박제) 채택 시 다음을 함께 박제:
- **거부 사유**: 왜 이번 Phase 자산에 들이지 않았는가 (YAGNI / Phase 제약 / 다른 추상화 레벨 / 1회성 등)
- **대체 처리 경로**: 어디에 어떻게 박제했는가 (best-practice/X.md / 헌법 §Y 보강 / 후속 Phase 이관 등)
- **재등장 시 처리 룰**: 같은 후보가 다시 등장하면 어떻게 처리할지

### 2-3. 거부도 SSOT인 이유

- "거부 결정"이 명시 박제 안 되면 다음 분해 시 같은 후보가 "처음 보는 아이디어" 로 재등장
- 재등장 시 다시 판단 비용 발생 + 한 번 거부됐다는 정보 손실 → 결정 일관성 깨짐
- "왜 안 했는가"는 "왜 했는가"와 동등한 SSOT 정보

### 2-4. 인시던트 증거

**Endurance Phase 1 분해 — 11번 후보 처리 (2026-05)**:
- 11번 후보: 검증 시나리오 자동화
- 채택 경로: ③ 자산 외 박제 (best-practice 박제 경로)
- 거부 사유: Phase 1 자산화하면 Phase 비대 + YAGNI 위반. 검증 자동화는 자산 layer가 아닌 워크플로우 layer 룰
- 대체 처리: best-practice/* 박제 (해당 문서는 별도 reflection 세션에서 박제)
- 결과: 11번 후보 재등장 차단

증상: Phase 1 자산 8개를 분해하고 그 중 8개 구현 완료한 시점에서 사용자가 GEMSTONE 스크린샷을 제시 → "이렇게 만들고 싶어" 단언. tl-dr SSOT 3축(Line 17 위젯 인벤토리 / Line 103 Phase 1 정의 / Line 122 Phase 4 이관 결정)이 사용자 의도와 모두 부분 어긋남 발견.

원인: tl-dr 작성 시 사용자에게 "구체적인 이미지/스크린샷/참조 대시보드가 있는가?" 묻지 않음. 사용자 일반 설명("엉드루 5단계 프레임워크")을 Phase 분해 직접 입력으로 사용.

룰:
1. 신규 페이지/주요 화면 자산 분해 시작 전, 사용자에게 "참조 이미지/스크린샷/경쟁 제품" 보유 여부 확인 의무
2. tl-dr SSOT 인용 시 "사용자가 직접 본 적 있는 화면 기준으로 정의된 항목인가?" 명시 검증
3. tl-dr 3축 이상 (위젯 인벤토리 / Phase 정의 / 이관 결정) 사이 일관성 자동 grep — 사용자 노출 위젯 이름이 3축 모두에 등장하는지
4. 자산 8건+ 구현 후 사용자 의도와 어긋남 발견 = 회귀 인시던트 — 회고 박제 + 메모리 룰 보강 의무

## Samantha 위임 prompt 패키지 가교 패턴

증상: Samantha 서브에이전트 컨텍스트에서 Agent 도구가 미노출 (Read·Glob·Grep만 노출) — 사만다가 직접 Joi·Friday·HAL·GERTY 호출 불가. 사만다 산출물은 `Agent(subagent_type=..., prompt=...)` 형식의 prompt **텍스트 패키지**.

원인: 서브에이전트 도구 권한 설계 — 사만다는 오케스트레이션·시니어 검토 책임만, 실제 Agent 호출은 메인 세션 권한. 이 구조 자체는 의도된 설계 (재귀 위임 방지·권한 boundary 명확화).

룰:

1. **메인 세션 가교 책임 4가지**:
   - 사만다 prompt 텍스트 패키지 → 실제 `Agent(subagent_type=..., prompt=...)` 호출
   - 산출물 verify (자산 시그니처 grep — 다른 자산 caller가 본 자산 실제 시그니처 일치 확인)
   - 트래커 갱신 (자산별 진행 상태 명시)
   - 자산별 git 커밋 (CLAUDE.md "파일별 개별 커밋" 룰)

2. **자산 간 SSOT 박제 grep 의무**: 자산 N 위임 후 N+1, N+2 자산 위임 시 N의 실제 산출 시그니처를 grep으로 caller에게 박제. 예: 자산 02 (모델 메타 API) 위임 후 자산 04·05·07이 02 prompt 텍스트가 아닌 **실제 구현된 02 시그니처**를 참조해야 함.

3. **자동 진행 게이트 패턴**: 사만다가 산출한 Step 흐름 중 "사용자 확인 시점" 만 정지. 나머지 Step은 메인 세션이 자동 진행. 게이트 정의:
   - 데이터 의존 검증 (예: OOS Sharpe / accuracy) → 사용자 확인 게이트
   - 시각 회귀 검증 (브라우저 검증) → 사용자 확인 게이트
   - 그 외 시그니처·타입·grep 검증 → 메인 세션 자동 통과

4. **양방 가교 룰**: 시니어 판단(디렉토리 명·자산 흡수·이관 결정 등)은 메인 세션이 사만다 권장을 **수정 가능**. 사만다 → 메인 단방향 명령 아님. 단, 수정 시 사만다에게 결과 통보 의무 (다음 위임 시 사만다 컨텍스트 갱신).

5. **인시던트 증거 (2026-05-16 Endurance Phase 1)**: 사만다가 Step 4~11 결정 패키지 산출 → 메인 세션이 Step 1·2·3 가교 실행 (30커밋). 자산 02 위임 후 04~07 caller grep으로 02 실제 시그니처 박제 — 자산 간 string snapshot 안티패턴(헌법 §2-0-1) 차단됨.
