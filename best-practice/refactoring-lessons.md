# 대규모 리팩토링 교훈 — 실전 체크리스트

게임 프로젝트의 결정론 런 시드 시스템 도입(38개 파일) 경험에서 도출했지만, **"전역 상태 제거", "결정론 보장", "대규모 인터페이스 도입" 유형의 리팩토링** 전반에 적용 가능한 교훈입니다. 웹 프로젝트(Next.js/TS)에도 동일하게 적용됩니다.

## 1. 플랜 단계 — 전수 검색이 먼저

**절대 원칙**: 심볼·패턴을 "제거/대체"하는 리팩토링은 **플랜 작성 이전에** 전수 grep을 돌리고, 결과를 **분류 테이블**로 정리해야 합니다.

```
Grep("Math\\.random|Date\\.now", output_mode="content")
→ 각 호출을 [비즈니스 로직 / UI 효과 / 테스트 / 의도적 유지] 4개 카테고리로 분류
→ 플랜 파일에 테이블로 고정
```

**왜?** 눈에 띄는 파일만 적으면 누락 발생. 동일 클래스/파일 내 **다중 메서드**는 grep 결과를 메서드별로 분류 의무.

## 2. 설계 단계 — "이중 안전망" 구조

결정론/재현성이 요구되는 시스템은 **두 겹의 보장**을 설계하세요:

1. **1차**: 결과 스냅샷을 디스크/DB에 저장
2. **2차**: `Hash(seed, label, context)` 기반 서브시드로 결과 재생성

"스냅샷 삭제 후에도 동일 결과"를 테스트하지 않으면 1차만 동작하는 설계인지 2차까지 동작하는지 구분 못 합니다.

## 3. 해시 결정성 함정 (JS/TS 환경)

- `Math.random()` — 비결정적, 시드 불가
- 객체 key 순서 — V8/Node 버전마다 다를 수 있음
- `JSON.stringify(obj)` — 키 순서 보장 안 됨 (정렬 필요)
- **반드시 FNV-1a 또는 SHA-256 수동 구현 또는 `crypto.subtle.digest` 사용**

## 4. 캐시 vs 재현성 — 상충 설계 주의

"서비스에서 RNG 인스턴스를 캐시하면 빠르지만, 같은 label로 재호출 시 **진행된 상태**가 반환되어 '스냅샷 삭제 후 재현' 시나리오가 깨집니다". 재현성 우선 서비스는 **매 호출마다 새 인스턴스 반환**이 원칙, 캐시는 명시적으로 금지하세요.

## 5. "새 객체 교체" 패턴의 필드 누락

`data.snapshot = factory.createSnapshot(...)` 류 코드는 **기존 필드 복사 누락**을 유발합니다.

**처방**:
- 새 인스턴스 교체 직전에 **보존할 필드를 로컬 변수로 꺼내두고** 교체 직후 재대입
- 또는 `previousState`를 팩토리 인자로 받아 필드별 명시 복사
- TS spread (`{ ...prev, ...next }`)는 안전하나 **필드 단위 옵트인 검토** 필요

## 6. 방어 분기는 반드시 로깅

"`runSeed === 0`이면 새 시드 생성" 류의 안전망 분기는 **`console.warn` 또는 구조화 로그를 반드시 동반**해야 합니다. 정상 플로우에서 트리거되면 결정론을 파괴합니다. 로그가 없으면 증상만 보이고 원인을 찾을 수 없습니다.

## 7. 두 버그가 서로를 가리는 경우

"매번 값이 바뀜" 증상은 종종 **중첩된 버그**입니다. 한 버그를 수정해도 다른 버그가 증상을 유지시키면 수정 효과가 안 보입니다.

**처방**: 단일 변화 포인트마다 `console.log` 추가 → 값의 변화 단계를 눈으로 추적 → 어느 단계에서 값이 달라지는지 특정 → 역추적으로 원인 발견.

## 8. Setter 주입 vs 생성자 주입

싱글턴/풀 객체에서 **생성 시점에 DI 파라미터가 아직 확정되지 않은 경우**(예: 라우트가 페이지 로드 전에는 없음)는 **Setter 주입 + Fallback label**이 더 안전합니다.

```typescript
let _rng: IRandom | null = null;
export function setRng(rng: IRandom) { _rng = rng; }
function getRng(): IRandom {
  return _rng ??= RandomService.forSubsystem("fallback");
}
```

Fallback label을 따로 두면 "주입이 실제로 호출되는지"를 운영 중에 감지할 수 있습니다.

## 12. 메서드 시그니처 변경 시 — "메서드 이름만 grep"

파라미터 제거·추가 시 **파라미터 값 기준 grep은 반드시 누락을 만든다**. 정규식은 "내가 상상한 패턴만" 찾기 때문:

- `,\s*false\s*\)` 검색 → 단일 인자 `foo(false)` 누락
- `\(false\)` 검색 → `foo(true)` 호출 누락
- 두 번째 인자 검색 → 명명 인자/객체 인자 `foo({ saveImmediately: false })` 누락
- 한 줄 형태 검색 → 줄바꿈 인자 `foo(\n  false\n)` 누락

**유일하게 안전한 패턴 — 메서드 이름 자체만 grep**:
```
\.markCompleted\(
```
결과를 **육안으로 검토**하여 괄호 안 인자 수가 새 시그니처와 맞는지 확인. 파라미터 값(true/false/변수)은 **전혀 검색하지 말 것**.

복수 메서드는 파이프로 1회 grep: `\.foo\(|\.bar\(|\.baz\(`

TypeScript에서 인터페이스/타입 시그니처 변경은 컴파일러가 잡아주지만, **string 키 또는 zod 스키마**는 컴파일 검증 밖이므로 grep 의무.

## 12.5 SSOT 단일 진입점 보존

동일 도메인 액션(저장, 분석 결과 캐싱 등)이 여러 호출처에 흩어져 있고 부수효과가 미묘하게 다르면 **단일 진입점(SSOT)으로 수렴**시킨다. 호출자 분기·오버로드는 빠르게 부수효과 누락을 만든다.

위임 프롬프트와 작업 종료 게이트에 그대로 인용 가능한 체크리스트:

- [ ] 동일 도메인 액션이 N곳에 흩어졌으면 **단일 진입점부터 식별** — 파라미터 차이만 다른 오버로드는 SSOT 후보
- [ ] 오버로드 추가 시 원본의 **부수효과 목록을 diff로 나열**, 새 오버로드가 모든 부수효과를 복제하는지 표로 매핑
- [ ] 호출자 분기가 타이밍 의존(예: `_currentItem` 같은 암묵 포인터)이면 SSOT를 **명시 파라미터(ID)** 로 강제하고 무파라미터 버전은 폐기
- [ ] SSOT 식별 grep 패턴: `\.methodName\(` (이름만), 결과를 **호출자별 부수효과 매트릭스**로 정리
- [ ] SSOT 통합 후 **레거시 진입점 즉시 제거** — 남기면 새 호출자가 다시 분기를 만든다
- [ ] 종료 게이트: `grep -rn "oldEntryPoint(" → 0건`을 세션 종료 직전 확인

## 13. 추출(Extract) 리팩토링의 책임 매핑

인라인 코드를 유틸/함수 호출로 **추출**할 때 **컴파일 성공은 동작 동등성을 보장하지 않는다**. 컴파일러는 로직 동등성을 검증하지 못하므로, 인라인이 갖고 있던 **모든 책임**이 추출된 곳에 옮겨졌는지 수동 검증 필수.

**대표 회귀 패턴**: `pickByWeight` 인라인을 `WeightUtil.pick` 호출로 교체했는데, 인라인이 수행하던 `minLevel/maxLevel` 필터링 책임이 유틸로 **이동하지 않고 사라짐**. 호출자의 사전 필터는 "0개 체크"로만 쓰이는 상태로 방치되어 **잘못된 항목이 등장**하는 회귀 버그가 통합 테스트에서야 발견.

### 추출 전 책임 목록화

인라인 코드의 다음 책임을 목록화:
- 입력 변환
- 필터링 / 검증
- 추첨 / 계산
- 폴백 처리
- 부수 효과 (로깅 등)

### 추출 후 책임 매핑

각 책임이 추출 후 어디로 이동했는지 확인:
- 유틸 내부로 이동?
- 호출자 측에 남음?
- **사라지지 않았는가?** ← 회귀 버그의 원흉

### 위험 신호 패턴

- "이전 코드가 받던 파라미터를 새 코드가 안 받는다" → 그 파라미터의 효과가 사라졌을 가능성
- "이전 호출자가 사전 필터를 했는데 새 유틸이 같은 필터를 갖지 않는다" → 책임 누락
- "리팩토링 직후 코드가 더 단순해 보인다" → 단순화가 아니라 **기능 누락**일 가능성

### 추출 위임 프롬프트 체크리스트

에이전트 위임 시 명시:
- [ ] 추출 전 인라인 코드의 모든 책임 목록화
- [ ] 추출 후 각 책임이 어디로 이동하는지 명시
- [ ] "기능 동등성 보존" 명시적 요구
- [ ] 의도된 동작 시나리오 1-2개 (예: "minLevel=6인 항목은 currentLevel=3에서 추첨되지 않아야 함")

## 15. 세션 종료 전 반드시 grep 전수 검증

Phase 마지막에 한 번 더:
```
Grep("[제거 대상 패턴]", path="src")
```
잔재가 남아있으면 한 번에 처리. 컴파일이 통과했다고 결정론이 작동한다는 보장 없음. **타입 검증과 동작 검증은 별개**.

## 17. 3단계 리팩토링 분할 기법 (Part A/B/C)

대규모 리팩토링은 **"신규 추가 → 기존 수정 → 정적 검증"** 3단계로 분할하면 각 단계가 컴파일 Green을 유지하며 `maxTurns` 절단 회복이 쉬워짐.

| Part | 책임 | 제약 |
|------|------|------|
| **A — 신규 파일만** | 새 인터페이스 + 구현체 별도 디렉토리에 추가 | 기존 파일 **무수정**, 단독 컴파일 Green |
| **B — 기존 파일 리팩토링** | Part A 산출물로 내부 구현 교체 | **공개 API 시그니처 유지** (wrapper 보호) |
| **C — 정적 검증** | 전/후 동등성 + 원칙 달성 read-only 검증 | 편집 권한 없음 |

**위임 프롬프트**: Part A "신규만", Part B "공개 API 유지", Part C "edit 금지, 보고 3섹션 이내". 각 Part 후 `git diff --stat` 확인.

## 18. 도메인 전문 컴포넌트 선탐색

"X 로직 참고" 지시를 받으면 **도메인 전문 컴포넌트가 이미 존재하는지 먼저 grep** (`*Form`, `*Table`, `*Provider`, `*Adapter`). 새로 만들기 전에 재사용 가능한 컴포넌트가 있는지 확인하는 것이 추출(Extract) 리팩토링의 출발점입니다.
